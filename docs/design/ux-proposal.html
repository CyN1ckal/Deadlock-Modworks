Deadlock Modworks · UX proposal

One app, two depths: a mod manager up front, a model workshop one click away

The features are solid. The layout follows the code's modules, so a player who only wants three skins in their game has to read a lot of it. This proposal reorganizes around what people come to do, keeps every expert tool, and changes very little underneath.

What I found

I read the page tabs, menus, panels and theme, and looked at the captured screenshots. These are the issues that cost a non-developer the most.

Navigation

Eight equal tabs, ordered by when each module was built. The two things most players want, Get mods and Mods → Apply to game, are tabs 7 and 8 on the far right. Model inspector and Multi view get the same weight as the core loop.

Two install paths

Players can enable a mod and press Apply to game, or build a VPK and copy it into addons by hand. The README's first-run steps teach the manual path first, so new users meet the harder route before the easy one.

Always-on sidebar

The Sources panel shows on every page, including Get mods and Mods where it has no job. It carries the library path, the game archive path, Share and Add shared. That is setup detail sitting in prime space.

Vocabulary

A user meets mod, source, package, archive, VPK, pack, skin, model, library, game archive, addons and citadel. Several mean nearly the same thing to a player.

Copy

Messages are precise and honest, written as disclaimers. The empty library leads with a paragraph about textures stored in the game archive before the user has done anything.

Hierarchy

Primary buttons (#2A5678) are barely distinct from normal ones (#2A3948). 6 px padding, one font size, no page headings. Every control looks equally important, so nothing reads as the next step.

theme.cpp, theme.hpp
State as sentences

Whether changes are applied, whether Deadlock is running, and whether gameinfo.gi loads addons are lines of coloured text. Game connection is a dot and a "..." button.

ModsPanel::DrawGameState
Repairs are hidden

After a game update, users must already know that skins can break and that a Skin repairs tab exists. The app knows the game changed but doesn't say so.

Principles

Goals before modulesNavigation names what a player wants to do, in the order they do it.
One happy pathDiscover → turn on → Apply → play. Everything else branches from it.
Group, don't hideExpert tools stay one click away in a labelled Tools section. Shortcuts and right-click menus keep working.
State is a componentGame status, pending changes and broken mods get persistent UI, not a sentence that scrolls away.
Say it, then explainLead with the action in plain words. Caveats move to tooltips and a "Learn more" link.

New structure

The top tab bar becomes a left navigation rail with two groups. The rail replaces the Sources sidebar, whose contents move to where they are used: the source list becomes a filter on Skins and Pack builder, and game and library settings move to Settings.

What changes on this screen

  • Switches, not checkboxes. A row reads as on or off at a glance. Disabled rows dim.
  • Profile actions live in the profile menu. New, Rename and Delete leave the toolbar. Enable all and Disable all move to the row's right-click menu and a multi-select bar.
  • Load order is a mode. The up/down arrows on every row become a "Load order" view with drag handles and the conflict list beside it. Most users never open it; the conflict badge tells them when it matters.
  • The Apply bar is the one primary action. It counts changes, names them, offers Undo, and explains why it's disabled.
  • gameinfo.gi stops being a warning line. If addons aren't loaded, Apply handles it with a one-time confirm: "Deadlock isn't set up to load mods yet. Modworks will add one line to gameinfo.gi."

Words

One noun per idea. A mod is a file you added. A skin is one model inside it. A pack is something you built. "Source", "package" and "archive" leave the main UI and stay in Tools and tooltips.

Visual system

Keep the palette; it already suits the game. Fix hierarchy with spacing, type size and a primary colour that stands out.

  • Primary goes from #2A5678 to #3B7DBF with white text. Use it once per screen.
  • Spacing: FramePadding 6×3 → 10×6, ItemSpacing 6×4 → 8×8, WindowPadding 6 → 16 on pages. Rounding 2 → 6 on cards and buttons.
  • Type: load a second atlas entry at 1.4× for page titles, and a bold weight. ImGui 1.91.9 has no per-call font sizes, so these are extra AddFontFromFileTTF calls next to the body font.
  • Icons: merge an icon font (Lucide or Material Symbols, both permissively licensed) into the body font with MergeMode. The rail, Apply bar and badges use them; menus mostly don't need them.
  • New widgets in ui.cpp: Toggle, Badge, NavItem, Banner, SplitButton. Each is a small custom draw with ImDrawList.

Keeping it powerful

Nothing is removed. The Tools group is visible by default, under a quieter label. A Settings › Interface › Show tools switch can collapse it for people who only play; I'd leave it on for existing installs and off for fresh ones only if you're comfortable with that split.

  • Every right-click menu stays, including copy hash, copy path and reveal in Explorer. Developer-only items (copy hash, snapshot id) move under a "Copy ▸" submenu so they don't lead.
  • Every shortcut stays. F1 still lists them.
  • Skins and Pack builder keep the dense grid/list switch and thumbnail size control; Tools pages keep their tables.
  • Status messages stay copyable. They move into a toast stack in the bottom right with "Copy" and "Dismiss".

Rollout

Ordered so each step ships on its own and the riskiest structural change comes after the cheap wins.

Phase 1copy and theme
  • New spacing, primary colour and title font in theme.cpp.
  • Reorder and rename tabs in DrawPageTabs; My mods and Discover first.
  • Rewrite empty states and status lines per the Words table.
  • Hide the Sources sidebar on My mods and Discover.
Phase 2My mods
  • Toggle, Badge and Banner widgets in ui.cpp.
  • Rebuild ModsPanel::DrawList as cards; move profile actions into the combo; Load order view.
  • Sticky Apply bar replacing DrawGameState's text lines.
Phase 3navigation
  • Left nav rail with icon font, replacing the tab bar and the Sources sidebar.
  • Game status card; game and library settings move to a Settings page.
  • Source filter moves into Skins and Pack builder.
Phase 4guided flows
  • First-run checklist.
  • Game-update banner that runs Analyze and offers "Fix n skins".
  • "Add to My mods" as the Pack builder's default action.
  • Refresh the screenshots and the README first-run steps to lead with Apply to game.

Decisions for you

Should Tools be collapsible for players?Grouped and always visible is safer for support and docs. A "Show tools" switch is cleaner for players who never touch them.
Renumber shortcuts now, or keep Ctrl+1–8 for one release?Renumbering matches the new order; keeping them avoids surprising current users.
Where to start?Phase 1 is a few hours and touches only theme, labels and copy. Phase 2 is where players feel the difference.
